# Decision record: figure export

This page answers: **"Why does a figure come out the way it does: why is a
legend never cut, why are axes laid out once from their text, why is the only
size limit the browser's canvas, and why are the point passes drawn in a
worker that keeps its WebGL contexts?"** It records the decisions with their
dates, what each replaced, and what is still open. How the module works is
{doc}`12_figure_export_architecture`, and this page does not repeat it.
Update this page in the same change as the code it describes.

## What it does now

Paths are under `cellucid/assets/js/app/ui/modules/figure-export/`.

1. **A figure reproduces the view** (camera, filters, colors, layers) as SVG
   or PNG. Heavy work runs only when the person previews or exports.
2. **Three SVG strategies**: every point a vector element (`full-vector`), a
   density-preserving reduction (`optimized-vector`), or the points
   rasterized into an image with everything else vector (`hybrid`).
3. **One layout call per export.** `computeFigureLayout(payload)`
   (`utils/layout.js`) lays the figure out for both renderers, so the PNG and
   the SVG cannot place anything differently.
4. **A legend and the axes are planned once, from measured text**
   (`components/legend-builder.js` `planLegend`, `components/axes-builder.js`
   `planFigureAxes`, `utils/text-measure.js`); the SVG and Canvas builders
   draw the plan and measure nothing.
5. **Every per-cell pass and every encode runs in the export worker**
   (`utils/figure-export-worker.js`). The point passes draw on WebGL2
   contexts the worker keeps for the page's lifetime; where a browser gives a
   worker no WebGL, the same handler draws the point passes on the page.
6. **The settings are one record of the `settings` state domain**, changed by
   the action `figure-export.set` and recorded by observation when a person
   changes them in the panel.
7. **The figure renderer also draws `view.picture`**, the picture an agent
   or the printable history report asks for.

## Decisions and why

### The worker, the pixels and the files

| Date | Decision | Why | Rules out |
|---|---|---|---|
| by 2026-10-21 | The worker keeps its WebGL2 contexts for the page's lifetime, one per antialiasing setting; a pass returns its frame with `transferToImageBitmap()` and the canvas shrinks to one pixel | Creating and losing a context per pass cost a context and a shader compile every time, and made WebKitGTK and WPE abort the page on a GL call made without a current context during the teardown | A context per pass |
| by 2026-10-26 | The page hands the composed canvas's pixels to the worker as an ImageData whose buffer is transferred, read in bands of rows with a yield between them (`pagePixelsInBands`), and the worker encodes it with `OffscreenCanvas.convertToBlob`, the encoder `toBlob` uses. Every image the page hands the worker to encode (the composed figure, a backdrop look's raster, a Hybrid point pass) crosses as pixels | An ImageBitmap of a page canvas was encoded by Linux WebKit (WPE, whose workers have no GL) without the canvas's pixels: a PNG figure held a blurred, magnified patch of the screen's floor grid and none of the figure, and a backdrop look's raster was entirely transparent. One read of a 300 dpi figure held the page about 40 ms, hence the bands (Measurements) | An ImageBitmap of a page canvas as the encoder's input; one whole read |
| by 2026-10-26 | Where the point pass is drawn follows the measured capability: the client asks the worker once whether it can create a WebGL2 context on an OffscreenCanvas, and draws the point passes on the page where it cannot. One rasterizer, no setting | WebKitGTK and WPE have no WebGL in workers, and some Safari releases returned no WebGL context to an OffscreenCanvas in a worker while the same context worked on the page (the bugs are named on the reference page) | Choosing the placement by browser name; a second rasterizer |
| 2026-11-10 (owner) | A legend entry is never cut: a legend is as large as its entries need, and the figure grows around it | Before, the box was capped at the plot's size and the builders cut names to their columns with "…" (the Suo dataset's `cell_type`, 69 categories, at 720 × 500; and a grid panel's legend of 69 entries drawn as swatches and "…") | A cap on the legend's box; names cut to a column |
| 2026-11-11 | Axes are laid out once, from their text: `planFigureAxes()` places every axis line, tick, tick label and axis label and gives the margins they need, and both renderers draw that plan | Before, the y label stood a fixed `5 + 8 + 1.15 x label` px from the axis and ran into wide tick labels (17 px ticks, 20 px label: "UMAP 2" over "-0.5"), the margins were a fixed 62 px at any text size (1 to 500 px), so large text was cut at the edge or ran into the legend, and the PNG put the y tick labels 2 px from their ticks where the SVG put them 8 px | Fixed margins or distances; a renderer that measures for itself |
| by 2026-11-12 | The only size limit is the browser's canvas: the PNG canvas is allocated at the figure's size and checked by drawing a pixel in its far corner and reading it back (`utils/figure-canvas.js`); where the browser cannot draw it, the export is refused before rendering with one sentence naming the size and the remedy | A million-category legend once asked for a canvas millions of pixels wide and the PNG never came; the cap that answered it cut every legend | A cap chosen by the app |
| by 2026-10-26 | The point raster is rendered at exactly the snapped device-pixel size of the plot and copied one to one | A raster drawn into the fractional rectangle (at 300 dpi a plot at x = 82 starts at 256.25) was resampled by the 2D canvas, a quarter-pixel blur whose bytes depended on the browser: on the hosted macOS Firefox runners one unchanged view exported before and after a kept view came and went differed by one level at the same few antialiased point edges, in every run | A raster drawn into a fractional rectangle |
| by 2026-11-12 | The point pass is drawn with the antialiasing the viewer is drawing with at the moment of the export (`viewer.getAntialiasing()`, carried in the render state), never a fixed value or one read at startup | Antialiasing is a live setting that also follows the dataset, and it changes the picture: 18% of pixels at point size 0.75 and 32% with ultra-light square points (Measurements), so a fixed `true` would publish a smoother cloud than the screen drew | A fixed antialiasing flag |
| by 2026-11-12 | The PNG renderer composes the figure in one synchronous run after every worker answer; a composition is never split across tasks | A composition flushed in pieces is rasterized with antialiased rules differently: about 1,400 pixels of the reference grid differed by up to 21 levels (measured on Suo) | Awaiting inside the composition |
| by 2026-11-12 | The point markup of the two vector strategies is encoded in the worker straight into a reused 1 MiB buffer whose contents become Blob parts; the SVG is assembled from Blob parts and never joined into one string | A million circles as a string is megabytes on the main thread: a full-vector SVG of the 561,947-cell dataset is about 65 MB of markup | Joining the points into one string |
| by 2026-11-12 | A batch ZIP checksums each entry 4 MiB at a time (`CRC_SLICE_BYTES`), one slice per task, with the shared CRC-32, and takes the entry Blobs themselves as its parts; the archive is the app's one ZIP writer's (`formats/zip/writer.js`: stored entries, fixed timestamps, ZIP64 fields where a size or offset needs them) | No batch is too large for the format, no slice keeps the main thread busy (one 4 MiB slice takes about 2 ms), and the bytes are never copied or held whole | A copy of each entry |
| by 2026-11-12 | With no export session open the worker and the page's drawing host end after the idle lifetime of `workers/idle-retirement.js` (`WORKER_IDLE_MS`, 10 seconds) and start again for the next export; a request outliving its export's abort rejects at once and the worker's late answer is discarded | A figure-export worker holds WebGL contexts, which the browser caps | Keeping the worker for the page's life |
| by 2026-11-12 | The depth sort of a requested sort order is an O(N) binned sort and is honored at every point count (`utils/point-projector.js`) | No reason is recorded | A sort refused or approximated above a size |

### Layout and composition

| Date | Decision | Why | Rules out |
|---|---|---|---|
| 2026-11-11 | The plan of the "axes laid out once" row above places the y tick labels a gap left of their ticks, centered on them at any size (the baseline 0.35 font sizes below the tick, half a digit's height; a fixed 4 px was centered at 12 px only); the y-axis label stands past the widest y tick label and the x-axis label under the x tick labels; a tick label at a plot's corner, or an axis label longer than its side, is reserved on that side too, and an axis label longer than its side starts at the plot's shared corner and runs on past the far end. The ticks are the nice values between the ends, at the finest nice step (1, 2, 2.5, 4 or 5 x 10^n) whose labels, measured with the figure's font, keep half an em apart, at most five, fewer as the axis shortens, one where two cannot fit | Nothing overlaps at any text size (1 to 500 px) | A layout of fixed distances; a renderer that places its own labels |
| 2026-11-11 | Axes are drawn only where they are rulers: a 1-D or 2-D view in planar navigation, looked at straight down its plane, every cell on it (`figureViewHasAxes()`, `figurePanelAxes()`). A 3-D view, in any navigation, or an orbited flat view has no axes and no axis margins, and the orientation widget shows its directions. `computeSourceAxisBounds()` gives the embedding coordinates the view's or the crop's edges show on the embedding's plane | Camera-space ticks on the focal plane were exact at one depth only and were read as UMAP coordinates: in a perspective picture of cells at many depths one plot length is a different distance at every depth. A grid's panels also came with X and Y rulers on a 3-D orbit view | Axes on a 3-D or orbited view |
| by 2026-11-12 | A plot takes the view's aspect inside the requested size, as the largest rectangle of that aspect, and the view fills it with the screen's own projection (`utils/plot-fit.js`); "Fit the cells" frames every cell a view draws with a small margin, so the plot takes the cells' shape, and the preview says when a plot's shape is 1.5 times off (`SHAPE_FAR`) | A 16:10 view exported at 720 x 500 drew its cells in a 720 x 450 band of a 720 x 500 plot while the axes spanned all 500 px; a figure keeps what the screen frames, so a pane narrowed by the chat or a grid gave narrow plots of a wide embedding with the cells in a band, and an agent once hid the person's sidebar to widen the panes | A letterbox; the pane's shape as the plot's |
| 2026-11-11 | A grid figure is a composition (`computeGridFigureLayout()`, `composeGrid()`): every panel's plot has one height and its own view's aspect; the requested size is the box the figure fits, the plot height being the largest whole number whose composition (plots, margins, labels, legends, title) fits, found by halving, and the figure is exactly that composition, never padded to the box; legends take room from the plots down to `PANEL_LEGEND_SHARE` (0.5) of the height they have without legends and never below 80 x 64 px (`PANEL_PLOT_MIN_WIDTH` x `PANEL_PLOT_MIN_HEIGHT`), and past that the figure grows | A figure of two tall views was the full requested size with narrow strips in its corner, of different heights (plots 108 x 255 and 140 x 325 px in a mostly empty 1400 x 800 canvas, and legend frames stretched to the plot's height around a few entries), because each legend took its width out of a cell before the plot was fitted | Padding the figure out to the box |
| 2026-11-11 | A grid's legends are arranged against the legend-free plot alone: when an arrangement does not keep to the box, every legend beside and then every legend below is tried and the first that keeps to it is drawn (`arrangementOf`; else the one reaching least past it) | A legend kept beside a plot that the legends then shrank was planned again in more columns: two wide views in an 800 x 600 box became 182 x 114 px strips beside 862 px legends in a figure 1,550 px wide; a portrait box of tall views drew 137 x 315 strips in a figure wider than the box | Planning a legend against a plot that later shrinks |
| 2026-11-11 | A panel title (`panelTitle`, letter plus view name) is one function: the layout measures it and widens its column, both renderers draw it, and it is never cut | The grid sized a column by plots, axis margins and legends, never by the title, and both renderers clipped it: "C. Neurog3 (endocrine pro" at 24 px in three columns (an agent's Figure 2 of Pancreas) | A title cut at the panel's edge |
| 2026-11-11 | The legend's least width beside the plot is in ems of its font (`LEGEND_MIN_EMS_BESIDE` = 10: 120 px at 12 px, 25 mm at 7 pt), and a legend asked beside the plot that would make a single-column figure wider than asked stands below it (`legendMovedBelow`) | A fixed 240 px (63 mm) left a single-column print figure's plot 15 mm wide; a legend of long names, or the vector field's key, beside a short plot came out 101 mm wide | A fixed pixel minimum |
| 2026-11-11 | A figure's size is one model (`utils/figure-size.js`) used by the layout, both renderers and the preview: the person or `figure-export.set` gives the width physically (millimetres, or a journal's column) and text in points; layout is in figure pixels of 1/96 inch; a PNG at D dpi is D / 96 device pixels a figure pixel and says D dpi (`pHYs`); an SVG states its size in millimetres with its `viewBox` in figure pixels; `view.picture` with source "export" says the size in millimetres and pixels. The record's version went to 3 (version 2 held a pixel box and pixel text sizes) | A bare pixel size is read as 1/72 inch by some editors, and an agent set 1800 for "180 mm" (10 px a mm) and got a figure 476 mm wide at 300 dpi, and twice did pixel-to-point arithmetic wrong; a layout program places a 300 dpi PNG at its size only if it says so | Converting pixels to points by hand |
| 2026-11-11 | The default width of a figure is double column, never a custom width measured off the window that saved it | Every sample dataset's starting view, saved at `screen-half` in a 1440 px window, came back as a custom 190.5 mm | A width measured off the window that saved it |

| Date | Decision | Why | Rules out |
|---|---|---|---|

The payload names the page (`selection.pageName`, required while cells are highlighted) | A dot alone vanished among cells colored like it; a reader who never saw the app read the cyan highlight of the germ cells over a gene's viridis as "the cells with high NANOS3" | A highlight with no legend entry; a ringless dot |
| 2026-11-10 | With every category shown, the title's field says so and does not list them; a grid whose panels are colored by different fields is titled by the dataset alone and each panel names its own field. The title names the filters on other fields ("LVL0: showing only Epithelial"), because the legend lists no category those filters leave empty and the title is where the figure says why. A filename names the color field once | A title read "cell_type: AXL+ and SIGLEC6+ DCs, B1 cells +67" over all 69 cell types, a grid of cell_type and organ panels was titled "... - organ", and a view carrying its field as its label gave `Atlas_cell_type_cell_type_<ts>.png` | A title that lists every category; the field written twice |
| 2026-11-11 | The vector field's key stands inside the plot's bottom-right corner only in a figure without a legend, and its field line wraps at its words to the plot's width | On a small plot the key covered the cells, and on a single-column figure (a plot 35 mm wide) "velocity: mean arrows of nearby cells" ran out of the plot and was cut at the figure's left edge | A key that covers cells or is cut |

### Points, color and the layers of the viewer

| Date | Decision | Why | Rules out |
|---|---|---|---|
| 2026-11-11 | A point's diameter in the vector strategies, every format's centroid discs and the preview is the shaders' sprite size for one point (`createViewportPointDiameter()`: `u_pointSize` mixed with its perspective size `pointScale / eyeDepth` by the size attenuation, clamped to 0.5 px and the pane's cap `renderState.pointSizeMax`), at the cell's depth; the raster renderers multiply `u_pointSize` by the view's per-LOD size multiplier (`scientificState.lodSizeMultiplier`) and `scalePointDiameterToRaster()` gives the diameter for a raster `s` times the viewport. The size is the exact product with no one-pixel floor: the shaders' own minimum (`POINT_SPRITE_MIN_PX`, 0.5 px) keeps a point visible, applied to the rendered size | The circles took `u_pointSize` as the pixel diameter, so at the default attenuation 0.8 a 3-D figure drew specks where the screen drew spheres 3 to 4 times larger, near and far alike (2026-11-11); `u_pointSize` is a scale and the rendered size is linear in it, so a floor inflates rather than protects, and the PNG renderer floored at 1 px where the hybrid SVG did not, so one view exported twice disagreed with itself (Measurements) | A pixel floor; a diameter independent of depth |
| 2026-11-11 | There is no near fade in the vector strategies: every cell is drawn whole | A near fade, shipped and removed on the owner's decision the same day (the row on {doc}`28_decisions_rendering_layers`), left the nearest cell out and the second translucent | A near fade |
| by 2026-11-12 | The viewer's atmospheric fog (Beer-Lambert, `rendering/shaders/fog-shaders.js`) is reproduced for the vector strategies (`utils/fog.js`: circle opacity, fog color toward the paper); the sphere-impostor lighting term has no flat-disc equivalent and is not reproduced, and the strategy hint says so | The `full` shader thins every point with distance, and `fogDensity` starts at 0.5, the depth cue a 3-D scatter reads by; the vector strategies project in JavaScript and used to emit every circle at its raw color, so foreground and background cells were indistinguishable and the depth axis was flattened | Vector strategies with no fog |
| 2026-11-11 | Annotation ink (title, ticks, axis labels, panel letters, legend text, plot frame, selection badge, the "No visible cells" notice) is derived from the figure's own background luminance, from two palettes mirrored across the luminance midpoint (`utils/figure-ink.js`); a transparent figure keeps the light palette | The ink was hard-coded near-black (`#111`) on a near-white frame: right on white paper and unreadable on any dark figure, including every `Background: Match viewer` export from `Grid (dark)` or `Black` | Fixed ink |
| 2026-11-11 | Color vision simulation uses the Machado, Oliveira and Fernandes (2009) full-severity matrices applied to linear RGB (`utils/colorblindness.js`) | The "Coblis" approximation on encoded values showed vivid cerulean and iris purple (the default palette's second and tenth colors) as plainly different under deuteranopia, where they look the same (CIE dE2000 1.0), so a figure a red-green colorblind reader cannot read passed the preview | The "Coblis" approximation |
| 2026-11-10 | The hybrid SVG draws its points at 300 dpi at the figure's size, as a 300 dpi PNG does, the resolution journals ask of images | A fixed 2x of the screen is about 192 dpi | A fixed 2x raster |
| by 2026-11-12 | The reference grid box is reproduced as vector rules (`<line>` elements and Canvas strokes), not a second raster layer: `drawGrid()` (`rendering/viewer.js`) paints six quads of half-extent `GRID_SIZE` by a pure line pattern with no fog term, and straight 3-D lines project to straight 2-D lines. Each rule is one opaque stroke in the shader's fragment color already composited at the plane's effective opacity over the figure's paper; a rule in several classes (minor + major + frame, or minor + major + origin) is emitted as nested concentric bands, widest first. PNG and SVG consume one geometry model | A full-vector SVG stays fully editable; the shader takes `max()` across the two rule families, so a crossing must be as dark as one rule, not two (hence opaque strokes) | A raster reference layer; translucent rules |
| by 2026-11-12 | The studio backdrop is reproduced as vectors from the viewer's own functions and constants (`rendering/studio-backdrop.js`): the pane geometry the viewer drew with travels in the render state (`renderState.backdrop`: floor height, whether the embedding is flat, data center and extents, glow center, device pixel ratio, settled surface), so the export never re-derives it; the surfaces drawn and the dot surface's place come from `resolveStudioSurfaceWeights` and `resolveStudioBackdropPlane`; floor rules are `<line>`s stroked with a linear gradient sampled at 24 points along each rule; dots are circles; the glow and pool are radial gradients under an affine `gradientTransform`; lattice families are enumerated only near the screen samples where each shows, with no ceiling on how far the plane runs, and marks fainter than half a code value are omitted; rules and dots are opaque; the glow lightens the viewer's own surface and is drawn only when the figure's paper is exactly that color, the pool is ink at a varying opacity and exact over any paper | The shader's strength varies along a rule (stage fade, grazing fade, lattice family weight), so one stroke color cannot match it | Re-deriving the pane geometry in the export |
| by 2026-11-12 | The backdrop looks (Atelier, Nebula, Abyss, Aurora, light and dark) are drawn again as a raster, not vectors: each pane's look travels frozen in the render state (`renderState.backdrop.look`: the look id, the data tints, the ambient clock and, for Atelier, the baked contact-shadow map) and `rendering/backdrops/backdrop-look-raster.js` draws it with the same renderer and shaders in a private WebGL2 context kept for the page (the sky bakes are deterministic, so re-baked they match the screen); each raster pixel maps to the pane NDC it shows through the points' own placement (`resolveBackdropLookPlacement()`), so the look stays registered with the points, under a crop too; the pixel density is the figure's; PNG draws it at device pixels under the points, SVG embeds one `<image class="cellucid-backdrop-look">` at the hybrid point raster's 2x density; a look is drawn only on the viewer's own paper (`Background: Match viewer`); the preview shows the last raster rendered for the same state and redraws when a new one lands | The looks are procedural rasters | Exporting a look as vectors; a look on another paper |
| by 2026-11-12 | The vector field is drawn in a figure as a still picture of arrows on a grid, as scVelo's `velocity_embedding_grid`: the cells the view shows with a vector, through its camera onto the plot; per node of a 40-across grid the Gaussian-weighted mean (sigma = half a step) over `max(1, weight)`, nodes under 1% of the 99th-percentile weight dropped, arrows scaled by their mean length to half a step (matplotlib's quiver autoscale), colored by mean speed over the field's largest through the overlay's color scheme and outlined in the paper's color, with a key (field, how it is drawn, speed range in the embedding's units); one plan (`planVectorFieldFigure`) is drawn by SVG, PNG and the preview; the engine reads the arrays (`readFigureVectorFields`) before the synchronous snapshot and the provenance names the field per panel | A figure needs a still picture of the flow; the export used to refuse with "Velocity overlay not exported" | Blocking the export on the velocity overlay |
| by 2026-11-12 | The fidelity dialog blocks an export before rendering for data layers only: missing WebGL2 or camera matrices for shader-accurate rasterization, an enabled connectivity overlay, any render mode other than Points, and an unreadable render-mode, background or velocity control. Interaction chrome (the orbit compass, lasso and selection-radius indicators, multiview title chips, the projectile sandbox) is never exported and never blocks; the Annotations block states it up front | Blocking on always-on chrome would make ordinary exports impossible | Blocking on chrome |

### The settings, the agent's preview and the file's record

| Date | Decision | Why | Rules out |
|---|---|---|---|
| by 2026-11-12 | The settings panel's record is the parameters of the action `figure-export.set` (`FIGURE_EXPORT_PARAMS`, snake_case by `figureExportParamsOf`); a person's change is recorded as one step by observation from the event that made it, by one observer of the whole panel (`observeSettings`, comparing the record with the one last recorded); a title and whether it follows the dataset, Auto text and the font sizes travel together so a burst of typing is one step; an agent, a notebook or a replay uses the action, which applies the record whole through `importSessionSettings` and refuses settings that do not go together; a number box half-way through an edit contributes its last valid value. `figure-export.get` reads the settings back by the names `figure-export.set` takes | A setting added to the record is a parameter at once (`tests/figure-export-session-settings-contract.test.mjs`); an agent that set the settings could not check them after the history or a session put them back | Per-control recording; partial application |
| by 2026-11-12 | A saved record of the current version is read setting by setting: a value this version cannot use restores everything else and is named in `unread` | A dataset's starting view and an hour-old session lost every figure setting to the single setting a reader refused (a version 2 that refused an SVG strategy left unchosen opened every sample on "Sample view unavailable") | Refusing a whole record for one value |
| 2026-11-13 | A figure-export settings record of any version but the current one (3) is refused whole on read: the panel keeps its settings and the restore says "Figure export settings: they were saved as version N, and this version of Cellucid reads version 3"; the rest of the session is restored. The version 1 and 2 upgrades of a saved record are removed; `figure-export.set` steps still upgrade through the action versions | There are no users yet and nothing writes version 1 or 2, so a read-time upgrade was a compatibility hold for no one | `RECORD_UPGRADES` kept; a silent drop of the record |
| by 2026-11-12 | Every SVG export requires an explicit point strategy and the app never changes Full Vector, Optimized Vector or Hybrid on data size, view dimension, renderer availability or a render failure; it does not override or block a valid vector choice because Hybrid would look closer to a shaded 3-D viewport. The strategy opens as Full vector (every point, editable), so Export never refuses an SVG for want of a choice. ## Known limits and open items

- **The point pass drawn in the worker and on the page can differ by a few
  pixels on one hosted renderer.** The story and what the spec attaches now
  are in {doc}`28_decisions_rendering_layers` ("Pixel differences on CI that
  no local GPU shows").
- **The reference grid, the studio backdrop and the looks each have bounded
  differences from the screen**, none carrying a data claim (the last rows of
  Measurements).
- **A Full Vector or Optimized Vector figure does not reproduce the
  sphere-impostor lighting of the 3-D shader**, which has no flat-disc
  equivalent; the strategy hint says so.
- **What a figure cannot draw** (the vector field's particles, which a figure
  draws as a still picture of arrows, and the connectivity edges) is only in a picture taken from the screen (`view.picture` with
  `source: "screen"`).
